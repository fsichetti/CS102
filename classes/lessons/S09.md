# Lesson 2
## Stack and heap memory
Two regions of memory, two answers to the same question: **where** does data go?

- **STACK** - local variables. Predictable lifespan, freed automatically.
- **HEAP** - objects that must outlive the call that created them.

(These are also the names of two data structures we will study later. There is a reason for that, but don't mix them up.)

### The stack: frames
The stack holds one block per *active* function call, called a **stack frame**. A frame contains, among other things: the function's arguments, its local variables, and its return value.

Frames are pushed and popped at the **top** only - never inserted or removed from the middle or bottom. The function currently executing is always the top frame.

(trace the stack for):
```java
public class StackExample {
  public static void main (String [] args ) {
      foo () ;
  }
  public static void foo (){
      bar( 15 );
      bar( 8 );
  }
  public static void bar ( int x ) {
      bat(x);
  }
  public static void bat ( int x ) {
      ...
  }
}
```

if we draw high addresses at the top, the stack memory typically grows from top to bottom, the heap from bottom to top.

### The heap: `new`
`new` never allocates on the stack. The stack must stay strictly ordered, but objects are created at arbitrary moments and must survive the frame that created them.

So `c = new Circle(5)` does two things:
1. the JVM finds a free contiguous region of the heap, reserves it, and returns the **address of its first byte**;
2. that address is stored in `c` - a reference, i.e. a stack slot holding an address.

**Arrays are objects too, so they always go on the heap.** `int[] a = new int[10];` puts one address on the stack and 40 contiguous bytes on the heap.

Watch the extra level for arrays of objects: `Circle[] cs = new Circle[10];` reserves a heap block of 10 *references*, all `null`. Each `cs[i] = new Circle(...)` is then its own separate heap allocation.

### Who frees the heap?
A stack frame is freed automatically when the function returns. Heap memory is not - it has no such moment.

In C you would call `free()` yourself, and forgetting is a memory leak. Java instead runs a **garbage collector**: it periodically finds heap objects that are no longer reachable from any reference and reclaims them.

```java
Circle c = new Circle(5);
c = new Circle(10);   // the first Circle is now unreachable - GC will reclaim it
```

Two consequences for us:
- You never free anything, and you cannot leak an unreachable object. But you *can* still waste memory by keeping references you no longer need alive (a data structure that never shrinks).
- You do not control **when** collection happens. It is not at the moment the last reference disappears.

# Java features for data structures

## Inheritance
A class can *extend* another, inheriting its fields and methods and adding or changing its own.
```
public class Shape {
    protected String color;

    public Shape ( String color ) { this.color = color; }

    public double area () { return 0; }
    public void setColor ( String c ) { color = c; }
}

public class Circle extends Shape {
    private double radius;

    public Circle ( double r, String color ) {
        super(color);            // must be the first statement
        this.radius = r;
    }

    @Override
    public double area () { return Math.PI * radius * radius; }
}
```
Points to make:
- `Circle` **is-a** `Shape`. Inheritance models specialization, not "code I want to reuse". (Counterexample to discuss: should `Stack` extend `ArrayList`? Java did this and it is considered a mistake - a stack that inherits `get(i)` is no longer a stack.)
- `super(...)` calls the parent constructor; the parent part of the object is built first.
- `setColor` is written once, in `Shape`, and every subclass gets it. That is the reuse half of inheritance; `area` is the specialization half.
- `@Override` is not required by the language. Write it anyway - the next section says why.
- `protected` = visible to subclasses. Access modifiers: `private`, (default/package), `protected`, `public`.
- Every class implicitly extends `Object`, which is why everything has `toString()`, `equals()`, `hashCode()`. We will care a lot about `equals` and `hashCode` when we get to hash tables.
- Java has **single inheritance**: one parent only. (Why? Diamond problem, though this enters back in another form)

## Polymorphism
Greek for "many forms": **one name, several behaviors**. Java has two kinds, and the only real difference is who decides which behavior runs, and when.

| | decided by | decided when | from what |
|---|---|---|---|
| overloading | the compiler | compile time | the argument list you wrote |
| overriding | the JVM | run time | the class of the object in the heap |

Overloading is settled once the program compiles and nothing about it can change afterwards. Overriding cannot be settled until the program is running. That is why, when someone says "polymorphism" with no qualifier, they mean the second one.

### Overloading: same name, different parameter list
```
public class Circle extends Shape {
    ...
    public Circle ( double r ) { this(r, "black"); }                // constructors overload too
    public double area ( double scale ) { return area() * scale; }  // different parameters
}
```
The compiler counts and types the arguments and picks. Overloaded constructors are the usual way to offer a default, and `this(...)` calls a sibling constructor while `super(...)` calls the parent's - either must be the first statement, so you cannot use both.

Q: which constructor does `new Circle(2)` pick, and when was that decided?
A: the one-argument one, at compile time from the argument list; it then delegates to the two-argument one.

### Overriding: same signature, subclass replaces the behavior
`Circle.area()` above already does this. Mark it `@Override`:
```
@Override
public double area () { return Math.PI * radius * radius; }
```
The annotation is optional, and the reason to write it is the failure it prevents. Rename it `Area`, or add a parameter by accident, and you have quietly written a *new* method that nobody calls - the program still compiles and `Shape.area()` still runs. `@Override` makes the compiler check your claim.

Q: what happens if you write `@Override` above `area ( double scale )`?
A: it stops compiling. Nothing in `Shape` has that signature, so there is nothing to override - exactly the mistake the annotation exists to catch.

### Static and dynamic types
Overriding on its own is just "the subclass replaced a method". It earns its keep when the variable is declared as the *parent* type, because then one piece of code drives objects of many classes.

A variable has a **static type** - what the compiler knows from the declaration - and a **dynamic type** - what is actually in the heap when the line runs. They need not match, and calls are dispatched on the dynamic one.
```
Shape [] shapes = { new Circle(1), new Square(2, "red"), new Circle(3) };

shapes[0].setColor("blue");                  // inherited, one version for everyone
System.out.println( shapes[0].area() );      // Circle's
System.out.println( shapes[1].area() );      // Square's
```
Every element has static type `Shape`. The compiler has no idea which class each one really is, and does not need one. That is what lets a single piece of code work with every implementation of a contract without knowing which one it was handed - we make that contract explicit in a moment.

(Draw the memory picture: array of references in the heap, pointing at objects of three different classes.)

The static type is also a *limit*: it decides what you are allowed to call.

Q: What are the members of `Circle`?
A: inherited from `Shape`: `color` and `setColor`. Its own: `radius`, two constructors, and both `area` methods.

Q: `Shape s = new Circle(2); s.area();` - which `area` runs? Which one does the *compiler* pick?
A: the compiler picks the no-argument signature, since that is all it can see through a `Shape` variable; at run time dynamic binding runs `Circle`'s version of it.

Q: Does `Shape s = new Circle(1)` work?
A: yes. Upcasting is always safe and implicit.

Q: Does `Circle c = (Circle) s` work?
A: downcasting is checked at run time and throws `ClassCastException` if wrong. Guard it with `instanceof`.

Q: why can't we call `s.radius` even though the object really is a `Circle`?
A: because `s` is of type `Shape`; its value can change at run time to a reference to a `Square`, which has no radius.

Q: does an instance of `Circle` occupy more stack memory than a `Shape`?
A: no - objects are always on the heap; the stack value is always a reference.

## Abstract classes and Interfaces
## Abstract classes
`Shape.area()` returning `0` is a lie - a generic shape has no area. Better: refuse to implement it, and refuse to let anyone instantiate `Shape`.
```
public abstract class Shape {
    protected String color;
    public Shape ( String color ) { this.color = color; }
    public Shape () { this("black"); }
    public abstract double area ();          // no body: subclasses must provide it
    public void setColor ( String c ) { color = c; }
}
```
- An abstract class **cannot be instantiated**, but can have constructors (called via `super`), fields, and fully implemented methods.
- A subclass must implement every abstract method, or be declared abstract itself.
- Use when subclasses genuinely share state and partial behavior. (We will do exactly this: an `AbstractList` holding a `size` field and implementing `isEmpty()` as `size() == 0`, with the storage left abstract.)

## Interfaces
An abstract `Shape` answers "what *is* this thing". A different question is "what can this thing *do*" - and the answer may cut across unrelated classes. A `Circle` can be drawn on screen, but so can a `Sprite` or a `Button`, and none of those is a `Shape`.

An **interface** is a pure contract: a list of methods, no bodies, no state.
```
public interface Drawable {
    void draw ();
    void setColor ( String c );
}

public class Circle extends Shape implements Drawable {
    private double radius;
    public Circle ( double r, String color ) { super(color); this.radius = r; }
    public Circle ( double r ) { this(r, "black"); }
    @Override
    public double area () { return Math.PI * radius * radius; }
    public void draw () { /* actually put pixels on screen */ }
    // setColor is inherited from Shape, and that is enough to satisfy Drawable
}
```
A class **extends** one class and **implements** any number of interfaces. Now `Circle` is usable as a `Shape` *and* as a `Drawable`, and a method taking a `Drawable` will happily accept a `Button` too.

### Why `setColor` and not a color field
`draw()` needs a color, so the obvious move is to demand one in the interface:
```
public interface Drawable {
    String color;      // does NOT compile
    void draw ();
}
```
Everything an interface declares is implicitly `public static final`, so `color` is not an instance field at all - it is a constant, it needs an initializer, and there is exactly *one* of it shared by every implementing class. `String color = "black";` does compile, but it gives every `Drawable` in the program the same, unchangeable color. That is not what we wanted.

**An interface cannot mandate state, only behavior.** So we demand the *behavior* instead: `void setColor(String c)`. Every `Drawable` must be able to change its color; *where it keeps it* is entirely the implementing class's business. `Circle` keeps it in a field inherited from `Shape`; a `Button` might forward it straight to the operating system and store nothing at all.

Note that `Circle` never writes a `setColor` - it inherits one from `Shape`, and an inherited method satisfies the interface just as well as a freshly written one.

Draw the split on the board:
- `Shape` (abstract class): **what it is.** Holds the fields, has constructors, supplies working code.
- `Drawable` (interface): **what it can do.** No fields, no constructor, no code - just a set of obligations that `Button` can also sign up to without being a `Shape`.

- Methods are implicitly `public abstract`; you cannot write a constructor.
- A class can implement **many** interfaces - this is how Java gets multiple inheritance without the diamond problem: with no state to inherit, there is nothing to conflict.
- An interface can extend other interfaces.
- Since Java 8 there are `default` methods with bodies - mention, don't dwell.

**Abstract class vs interface**: is-a with shared implementation → abstract class. Can-do capability, possibly across unrelated types → interface. Two from the standard library that we will use constantly:
- `Comparable` with `int compareTo(Object other)` - "I know how to order myself against others". Every sorting algorithm we write will demand it.
- `Iterable` / `Iterator` - what actually makes the for-each loop work. Show that `for (Shape s : shapes)` desugars into `hasNext()`/`next()` calls.

Abstract class: single inheritance via extends, has a constructor, and can carry mutable state
Interface: multiple inheritance via implements, cannot have a constructor, and does not carry state (any field declared within an interface is implicitly public, static, and final)

Q: `String` implements `Comparable`. Why is that enough for `Arrays.sort` to sort strings, without `Arrays.sort` knowing anything about strings?

This is how we will define every ADT in the course: the interface is the contract, the class is one way of honoring it.
```
public interface Container {
    void add ( Object item );
    Object remove ();
    boolean isEmpty ();
    int size ();
}

public class ArrayStack implements Container { ... }
public class LinkedQueue implements Container { ... }
```
But look at what we were forced to write, and at `compareTo(Object other)`. Everything goes in and comes out as an `Object`, so the caller has to cast, and nothing stops them casting wrong. That is the problem the next section fixes.

## Generics
Suppose we want a class holding two values of the same type:
```
public class CirclePair {
    private Circle first, second;
    public CirclePair ( Circle a, Circle b ) { first = a; second = b; }
    public Circle getFirst () { return first; }
}
```
Fine, but the moment we want a pair of `String`s we copy-paste the whole thing and change one word, and again for every other type.

The alternative before generics was to store `Object`s and cast on the way out. That compiles, but nothing stops us putting a `String` in and pulling an `Integer` out, and nothing stops us mixing two unrelated types into the same pair - so the mistake surfaces as a crash at runtime rather than an error at compile time.

Generics are parameterized classes: the *user* of the class names the type, and the compiler enforces it.
```
public class Pair<T> {
    private T first, second;
    public Pair ( T a, T b ) { first = a; second = b; }
    public T getFirst () { return first; }
}

Pair<Circle> p = new Pair<>(c1, c2);      // diamond: the type is inferred
```

Now `Container<String> c = new ArrayStack<>();` rejects `c.add(42)` at compile time, and `c.remove()` needs no cast. Same for the standard library: `Comparable<T>` really declares `compareTo(T other)`, and `Iterable<T>` hands you a `T` per iteration.
- `T` is a **type parameter**, a placeholder filled in at each use site. Conventions: `T` type, `E` element, `K`/`V` key/value.
- Bounded types: `<T extends Shape>` - T may be any type that is a `Shape`, which is exactly what lets the method body call `area()` on it. Without a bound, `T` is only known to be an `Object`.
- Generic methods: `public static <T> void swap ( T[] a, int i, int j )`.
- **Type erasure**: generics are a compile-time fiction. The JVM sees `Object`. Consequences to state plainly (they *will* hit these in assignments):
  - `new T[10]` does not compile. Workaround: `(T[]) new Object[10]` plus a `@SuppressWarnings`.
  - `Box<String>` and `Box<Integer>` are the same class at runtime.
- Generics do not work with primitives: `Box<int>` is illegal, use `Box<Integer>` and let autoboxing handle it. Every boxed `int` becomes a heap object with a reference pointing at it - go back to the memory drawings and show what an `int[]` and a `Box<Integer>[]` really look like.
