## Exception handling
Half of designing an ADT is deciding what happens when the operation makes no sense. `pop()` on an empty stack: return `null`? return a sentinel? crash? Usually **throw**, because then the caller cannot ignore it.

Board, one line:
```
if ( isEmpty() ) throw new NoSuchElementException("pop from empty stack");
```
- An exception is an object; throwing it unwinds the stack frame by frame until a matching `catch` is found. **Tie back to the stack section**: the same stack we drew, being popped in a hurry.
- Hierarchy: `Throwable` → `Error` (don't catch) and `Exception` → `RuntimeException`.
- **Checked** (declare with `throws`, or catch - e.g. `IOException`) vs **unchecked** (`RuntimeException` and friends: `NullPointerException`, `IndexOutOfBoundsException`, and the `ClassCastException` that killed ch2 in the lab).
- Rule of thumb: unchecked = programmer bug in the caller; checked = the world outside the program failed. ch2 asked you to turn the first kind into a *compile* error - always the better fix when it is available.
- Custom exceptions: `class EmptyStructureException extends RuntimeException` - one line, and error messages become self-documenting.
- `try` / `catch` / `finally`: describe the shape aloud, we write it in a minute as part of the I/O block. `finally` runs whether or not we threw - clean-up goes there.
- Anti-pattern to name explicitly: `catch (Exception e) {}`. Swallowing an exception turns a loud failure into a silent wrong answer - the ch3/ch6/ch7 category, and the worst one to debug.

## File I/O
Brief - the point here is only that this is where checked exceptions stop being theoretical. Detail, and practice problems, in the writeup they read offline.

Data has to come from somewhere. Two classes, and they are both shapes you already know:
```
Scanner in = new Scanner( new File("data.txt") );      // instead of System.in
PrintWriter out = new PrintWriter( "out.txt" );        // instead of System.out
```
- `Scanner` on a `File` behaves exactly as on the keyboard: same `hasNextLine()` / `nextLine()`, same `hasNextInt()` / `nextInt()`. The `has...` methods are how you detect the end of the file.
- `PrintWriter` gives you the same `println` / `printf` you have used since CS101. It **buffers**, so without `close()` the file is usually empty - the number one "my code works but the file is empty" bug.
- **Both constructors throw `FileNotFoundException`, and it is checked.** The compiler will not let you write either line without catching it or declaring `throws`. That is the whole reason I put exceptions first: a missing file is exactly the case of "the world outside the program failed", and Java makes it impossible to ignore.
- `close()` never runs if an exception is thrown first - and this is **the prototypical use of `finally`**, so collect on the promise made two sections ago. Clean-up that must happen on *both* paths is exactly what `finally { in.close(); }` was invented for; a file left open is the textbook example of the thing you cannot afford to skip on the way out.
- The modern shape folds that `finally` into the `try` itself: declare the resources in the parentheses, `try ( ... ) { ... }`, and they are closed either way. Mention it, do not dwell.

# Searching and algorithm analysis

## Motivation: the phone book
Before any code. A phone book, 1000 pages, find one name.
- **Take 1**: page 1, is it here? no, page 2... Expect ~800-900 page turns. Go to 10 000 pages: ~8000-9000. Ten times the book, ten times the work.
- **Take 2**: flip 10 pages at a time, back up when you overshoot. Feels much better. It is not: 10 000 pages still costs ~10x what 1000 pages costs. We divided the work by a constant, we did not change how it *scales*.
- **Take 3** (next time): open the middle, throw away half. 1000 pages -> 10 turns. 10 000 pages -> 14 turns.

The point of the whole unit is on the board right there: take 1 and take 2 are *the same algorithm* for our purposes, take 3 is a different animal. We need a language that says that.

## Linear search
The only thing you can do on unordered data. Check every position until you find it, or until you run out.
```
public static int linearSearch ( int[] a, int key ) {
    for ( int i = 0; i < a.length; i++ )
        if ( a[i] == key )
            return i;
    return -1;            // sentinel: "not here"
}
```
- Returns the *index*, not `true`/`false` - strictly more useful, and costs nothing.
- `-1` as "not found" is a convention, not a law. It works because `-1` is never a valid index. Compare with `Optional`, or with throwing - we chose the boring option.
- **If the key is absent we cannot know that until we have looked everywhere.** Say this out loud, it is the whole worst case.

For objects, one line changes and one line gets added:
```
public static int linearSearch ( Point[] points, Point p ) {
    if ( p == null ) return -1;
    for ( int i = 0; i < points.length; i++ )
        if ( p.equals(points[i]) )
            return i;
    return -1;
}
```
- **`.equals()`, not `==`.** This is the third leftover from the lab, and *this* is the line where it bites - so do it here, not in the abstract.
  - `==` on references compares **addresses**: it asks "is this the very same object?". For objects that were built separately it is `false` even when they are identical, and the search silently returns `-1`.
  - ch3 `WordCount` was this exact bug in miniature: `sample == target` printed `true` because two identical literals share one interned object, but `words[i] == target` was `false` because `split()` built fresh `String`s. **The sanity check passed and told them nothing** - that is what made it a hard bug.
  - `Object.equals` **is** `==` until someone overrides it. So a `Point` with no `equals` makes this method fail to find a point that is demonstrably in the array. Overriding `equals` is not decoration; it is what makes your type searchable.
  - Q: the `int[]` version above used `==` and was correct. Why?  A: `int` is a primitive - no reference, no address, `==` compares values.
- `p.equals(points[i])` and not `points[i].equals(p)`: the array may hold `null`s, `p` we already checked. Free null-safety by ordering the receiver.
- Note it works on *unsorted* data and needs only `equals`, no ordering. That is the price we pay and the flexibility we buy.

Q: our data is sorted and the key is absent. Can linear search stop early? What does that change, and what does it not change?

## Counting operations
We want to compare algorithms without running them. Running them measures the machine, the JVM warm-up, and what else was open - not the algorithm.

So: **pick one representative operation, and count it as a function of the input size N.**

For search the natural unit is the **comparison** (`a[i] == key`). For sorting it will be comparisons and swaps. The choice is ours, as long as it is the operation that dominates.

Count the body of linear search, honestly, for an array of size N where the key is absent:

| line | times executed |
|---|---|
| `i = 0` | 1 |
| `i < a.length` | N+1 |
| `i++` | N |
| `a[i] == key` | N |
| `return -1` | 1 |

Total ~ 3N + 3 "steps". Now do it again assuming the compiler keeps `a.length` in a register, or that `i++` is free, or count only comparisons - you get 3N+3, or 2N+2, or N.

**All four answers are equally correct and equally useless in detail.** What survives every version of the count is: *it is a constant times N, plus a constant*. That robustness is exactly why we throw the constants away.

What we do **not** count:
- Anything that happens a fixed number of times regardless of N (setup, the final `return`).
- The cost of one operation in nanoseconds - that is hardware.
- Constant factors - that is the compiler, the language, the machine.

What we **do** count: how the number of operations *grows* when N grows. Doubling test: double N, what happens to the count?

| N | linear search comparisons | double N -> |
|---|---|---|
| 100 | 100 | |
| 200 | 200 | x2 |
| 400 | 400 | x2 |

## Best, worst, average case
Three different questions about **the same algorithm** on inputs of the **same size** N. The algorithm does not change - only which input of size N we hand it.

Linear search, array of size N:
- **Best case**: the key is at index 0. **1** comparison. Independent of N -> constant.
- **Worst case**: the key is at index N-1, or absent. **N** comparisons.
- **Average case**: needs an assumption about the *distribution of inputs*, and this is where people get sloppy. Assume the key is present and equally likely to be at any of the N positions:

```
key at index 0   -> 1 comparison
key at index 1   -> 2 comparisons
...
key at index N-1 -> N comparisons

average = (1 + 2 + ... + N) / N = [N(N+1)/2] / N = (N+1)/2
```
Roughly N/2. **Half of N is still a constant times N** - the average case is linear, same as the worst. Draw this: cutting the work in half does not bend the line, it tilts it.

Drop the assumption and the answer changes: if the key is absent half the time, the average is around 3N/4. Still linear. The conclusion is robust, the arithmetic is not - which is the lesson.

- Best case is almost never interesting. It is a single lucky input and it flatters every algorithm (bubble sort has a great best case).
- **Worst case is the default** when we say "the complexity of X". It is a guarantee: *no input of size N can do worse than this*. Everything else is a hope.
- Average case is what you actually experience, but it requires knowing your input distribution, and usually harder math.

Q: does an algorithm with a better average case ever beat one with a better worst case? When would you deploy each? (Quicksort is coming, this is not idle.)

## Big-O
The notation that formalises "throw away the constants and keep the growth".

Informally: **f(N) is O(g(N)) if f grows no faster than g, ignoring constant factors.**

Formally, for the board: f(N) is O(g(N)) if there exist constants c > 0 and N0 such that
```
f(N) <= c * g(N)   for all N >= N0
```
Two escape hatches in that definition, both doing real work:
- `c` lets us ignore constant factors - 3N+3 and N and 100N are all O(N).
- `N0` lets us ignore small inputs - we only care what happens *eventually*. Nobody optimises for N = 5.

### The definition, properly - for the mathematically inclined
```
f(x) = O(g(x))   iff   there exists M > 0 such that   |f(x)| <= M g(x)
```
That is the whole statement. Written out with the quantifiers, and with the "eventually" made explicit:
```
exists M > 0,  exists x0,  for all x >= x0 :   |f(x)| <= M g(x)
```
- `M` is doing the "ignore constant factors" job, `x0` the "ignore small inputs" job. Some books state it without `x0`, quantifying over the whole domain; for functions that are eventually well behaved the two agree, and `x0` is the version that matches how we actually use it.
- Note the absolute value is only on `f`. `g` is the yardstick and is taken positive - `N`, `N^2`, `log N` all are, at least past a small `x0`.
- **In our case it reduces further.** `f` counts operations, so `f >= 0` and `|f| = f`, and the definition is just `f(N) <= M g(N)` for large `N`. The bars are there for the general statement, where `f` may be any real-valued function; they do no work for us.
- **The `=` is an abuse of notation.** `O(g)` is a *set of functions*; the honest statement is `f` ∈ `O(g)`. That is why `O(N) = O(N^2)` reads as true left-to-right and as nonsense right-to-left - it was never an equality.
- Usually quicker in practice: if `lim (x -> inf) f(x)/g(x)` exists and is finite, then `f = O(g)`. If that limit is `0`, `f` grows *strictly* slower - that is little-o. If it is a nonzero constant, the two grow at the same rate.
- **A proof, so they see the quantifiers do actual work.** Claim `3N + 3 = O(N)`. Take `M = 4` and `N0 = 3`. For `N >= 3` we have `3 <= N`, so `3N + 3 <= 3N + N = 4N`. Done. Every big-O proof is this short: exhibit an `M` and an `N0`, then one inequality.
- The two siblings, since someone always asks:
  - **Ω(g)** - lower bound: `f = Ω(g)` iff `g = O(f)`.
  - **Θ(g)** - both at once: `f = Θ(g)` iff `f = O(g)` and `f = Ω(g)`.
  - When we say "linear search is O(N)" we almost always mean **Θ(N)**. Saying O is sloppy but standard, and harmless as long as you know you are doing it.

Mechanically, to go from a count to a big-O:
1. Drop all lower-order terms. `3N + 3` -> `3N`; `N^2 + 100N` -> `N^2`.
2. Drop the constant factor. `3N` -> `N`.
3. Write `O(N)`.

So linear search is **O(N)** in the worst and average case, **O(1)** in the best case.

Two things to say explicitly, because both get mangled:
- Big-O is an **upper bound**. "Linear search is O(N^2)" is *true* and useless. We always quote the tightest bound we know.
- **Big-O and worst case are two independent axes.** You can give a big-O for the best case, and people do. "Worst case O(N)" is one full statement; "O(N)" alone means worst case by convention.

### The classes we will use all semester
| | name | example | N=10 | N=1000 | N=10^6 |
|---|---|---|---|---|---|
| O(1) | constant | array index `a[i]` | 1 | 1 | 1 |
| O(log N) | logarithmic | binary search | 3 | 10 | 20 |
| O(N) | linear | linear search | 10 | 1000 | 10^6 |
| O(N log N) | linearithmic | good sorting | 33 | 10^4 | 2x10^7 |
| O(N^2) | quadratic | nested loop, naive sorts | 100 | 10^6 | 10^12 |
| O(2^N) | exponential | brute-force subsets | 1024 | *don't* | *don't* |

Make the last row real: at a billion operations per second, 2^N for N=100 outlives the universe. This is why the constant factor is not where the money is.

### Reading it off the code
Fast rules, enough for now:
- Straight-line code, no loops: O(1).
- One loop over N: O(N).
- Two nested loops over N: O(N^2). Nested loops *multiply*.
- Two sequential loops over N: O(N + N) = O(N). Sequential blocks *add*, then the largest one wins.
- A loop that halves N each time: O(log N).
- A loop calling an O(N) method inside: O(N^2). **Look inside the calls** - this is the one they will miss. `list.get(i)` inside a loop over a linked list.

## If there is time: counting practice
Four short ones. For each: **count first, then name the class.** Do not let them pattern-match on the shape of the code - that is the habit we are trying to prevent.

### 1. The triangular loop
Check an array for duplicates by comparing every pair.
```
for ( int i = 0; i < n; i++ )
    for ( int j = i+1; j < n; j++ )
        if ( a[i] == a[j] ) ...
```
The inner loop does not run `n` times. It runs `n-1`, then `n-2`, ... then `1`:
```
(n-1) + (n-2) + ... + 1 = n(n-1)/2 = N^2/2 - N/2
```
- Drop the lower-order term, drop the `1/2`: **O(N^2)**.
- The lesson: we did *half* the work of the full double loop, and it changed **nothing**. Same curve, half the constant. Go back to the doubling test - double `n` and the count still quadruples.

### 2. Sequential vs nested
```
for (i...) { ... }        for (i...)
for (j...) { ... }            for (j...) { ... }
```
- Left: `N + N = 2N` → **O(N)**. Sequential blocks **add**, and then the largest one swallows the rest.
- Right: `N * N` → **O(N^2)**. Nested loops **multiply**.
- Same two loops, same lines of code, completely different algorithm. Structure is what matters, not volume.

### 3. Loops that are not what they look like
```
for ( int i = 0; i < n; i++ )          // (a)
    for ( int j = 0; j < 100; j++ )
        ...

for ( int i = n; i > 1; i = i/2 )      // (b)
    ...
```
- (a) is nested, and it is **O(N)**, not `O(N^2)`. The inner loop does not depend on `n`, so it is a constant - `100N`, and the `100` goes. **Nested does not automatically mean squared.**
- (b) runs `n, n/2, n/4, ...` until it reaches 1 - that is `log2 N` iterations, so **O(log N)**. Same halving argument we will use for binary search next time.

### 4. The cost you cannot see
```
for ( int i = 0; i < n; i++ )
    linearSearch( a, b[i] );
```
- One loop, so it *looks* linear. But each call is `O(N)` on its own, so the total is `N * N` = **O(N^2)**. **Always look inside the call.**
- The same trap with a familiar face:
```
String result = "";
for ( int i = 0; i < n; i++ )
    result += "a";
```
  Strings are immutable, so every `+=` builds a **new** string and copies everything so far: `1 + 2 + ... + N = N(N+1)/2` characters copied. **O(N^2)** for what looks like a single loop appending one character.
  This is exactly the `repeatstring` demo - `generateAString1` vs `StringBuilder`. They have already *seen* the timings; now they can explain them.
